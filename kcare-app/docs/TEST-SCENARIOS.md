# 테스트 계정 시나리오 (베타 · 폰 3대)

테스트 계정 세 개로 실제 저장(Supabase)이 되는지 사람이 직접 확인하는 순서다.
같은 흐름을 자동 검사로도 돌려 모두 통과했다 (2026-09-30 · 로컬 Postgres + PostgREST 로 Supabase 흉내).

## 준비

| 폰 | 아이디 | 로그인하면 |
|---|---|---|
| 폰 1 | `test-guardian` (보호자) | `/family` |
| 폰 2 | `test-elder` (어르신) | `/elder` |
| 폰 3 | `test-concierge` (컨시어지 · 관제 화면도 이 폰으로) | `/concierge` |

- 비밀번호는 셋 다 `BETA_TEST_PASSWORD` 값 (관리자에게 받는다).
- 셋이 **테스트 가구 1** 을 같이 쓴다. 한 폰에서 한 일이 다른 폰에 **몇 초 안에** 뜬다
  (화면을 만지고 있으면 4초 · 2분 넘게 가만히 두면 10초 간격으로 가져온다).
- 처음부터 다시 하려면: 시연 허브(`/`) → **↺ 테스트 가구 기록 비우기**.
- 지금 어느 계정인지는 어르신·컨시어지 화면 오른쪽 위(● 이름), 보호자는 마이 탭에서 본다.
  점이 초록이면 서버에 저장 중, 주황이면 확인이 필요하다.

## Supabase 에서 확인

Table Editor 에서:

- `activity` — 누가 · 언제 · 무엇을 (예: `elder | 해주세요 요청 · 즉시 방문 요청`)
- `households` — `version` 이 저장할 때마다 오른다 · `updated_by` 는 마지막으로 저장한 계정
- `signups` · `payments` · `accounts`

SQL Editor 에서 최근 50줄: `select created_at, role, summary from activity order by id desc limit 50;`

## 알고 있는 제약 (버그 아님)

- 어르신 건강 수치 · 복약 통계 · 담당 컨시어지 이름 · 마음사서함 기본 메시지 같은 **고정 값은 목업**이다.
  테스트 계정이 만드는 것(요청 · 일정 · 음성 · 주문 · 결제 · SOS · 가입 신청)만 서버에 쌓인다.
- 관제 화면의 일부 저장(요청 관리 메모 · 병원 편집 · SOS 사건 진행)은 **그 기기에만** 남는다 (데모와는 따로).
- 같은 항목을 두 폰이 동시에 **고치면**(추가가 아니라 수정) 나중에 저장한 쪽이 남는다.
- 로그인 시도 횟수 제한이 없다 — 비밀번호는 20자 이상 무작위로.

## 문제를 알릴 때

폰 번호(1·2·3) · 계정 · 시각 · 누른 것 · 화면 캡처(비밀번호 · 키는 가리고).
