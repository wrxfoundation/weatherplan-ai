## 입구(소스) 규칙 — 방문의 첫 문서 요청에서 한 번

1. `utm_source` 가 있으면 그것(매체 = `utm_medium`, 없으면 `(not set)` · 캠페인 = `utm_campaign`) — KOL 링크 `?promo=…&utm_source=핸들` 도 여기
2. 없고 `promo` 만 있으면 `promo:코드`
3. 없으면 리퍼러 **호스트**(www. 뗌). 구글 · 네이버 · 다음 · 빙 · 야후 · 덕덕고는 이름으로, 매체 `organic`. 나머지는 매체 `referral`
4. 리퍼러도 없으면 `(direct)` — 주소 직접 입력, 텔레그램·카카오톡 앱 안 브라우저처럼 리퍼러를 안 보내는 곳
5. 우리 주소(`*.wellbian.io` · `*.wellbianlabs.io`)에서 온 요청과 리퍼러 없는 재방문은 **새 입구가 아니다** — 30분 쿠키에 남은 입구를 잇는다
   (GA 가 직접 유입으로 캠페인을 덮어쓰지 않는 것과 같은 원리). 쿠키도 없는 사이트 안 이동은 `(internal)` — 휴대폰 망 전환으로 방문자 해시가 새로 생긴 경우 등

방문자 한 명(하루 해시)은 **하루에 한 소스**로만 센다. 그래서 소스별 방문자 합 = 그날 방문자, 소스별 페이지뷰 합 = 그날 페이지뷰(기록을 켠 날부터).
화면 전환(RSC) · 미리 불러오기 · API · POST 는 입구가 아니다 — 기존 페이지뷰 정의(레이아웃이 도는 문서 요청)와 같다.

## 카드

- 방문자 / 페이지뷰 전환 · 소스 찾기(소스·매체 글자) · 줄 = 소스(매체는 작은 글씨), 칸 = 날짜(**최근 날이 왼쪽** — 위 일일 표와 같은 순서) · 합계 줄
- 칸 색은 브랜드 남색 한 가지의 옅고 짙음(로그 눈금) · `(direct)` · `(internal)` · `(기록 전)` 은 흐리게(우리가 움직일 수 없는 입구)
- 표는 가로·세로로 넘기고 소스 열·머리 줄이 고정된다

## 개인정보 · 부하

- 새로 저장하는 것은 소스 · 매체 · 캠페인 문자열뿐이다. 리퍼러 **전체 주소는 저장하지 않는다**(쿼리에 개인정보가 섞일 수 있다). IP · UA 원문 미저장은 그대로.
- 쿠키 `wb_src`: 30분, HttpOnly, 값은 `소스|매체|캠페인` — 사람을 가리키는 식별자가 아니다.
  개인정보 처리방침에 쿠키 목록이 있으면 한 줄 더한다: 「wb_src — 유입 경로(광고 · 링크 출처) 집계, 30분」.
- 부하: 페이지뷰당 쿼리 수는 그대로(방문자 UPSERT 에 열 3개). 미들웨어는 문자열 처리만 한다.

## GA 와 숫자가 다른 이유

자체 계측 방문자는 「하루 · IP + UA」 해시, GA 는 브라우저 쿠키 기준 사용자 · 세션이다. 봇 거르는 방식이 다르고, 광고 차단기는 GA 만 막는다
(자체 계측은 서버에서 센다). 그래서 두 숫자는 같아지지 않는다 — 추이와 소스 구성을 비교하는 용도로 본다.
