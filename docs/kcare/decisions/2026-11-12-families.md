# 2026-11-12 — 가족마다 기록 나누기 ("가입 코드가 달라도 모두 같은 관제 · 같은 컨시어지로 묶인다")

정식 오픈 일정 공유(11/12)의 1번 항목이다.

> 베타모드에서 서로 다른 가입코드로 10명 정도 가입시켜 테스트했는데, 가입코드가 달라도 모든 계정이 같은 관제 · 같은 컨시어지로
> 자동 지정되어 있습니다. (목업용으로 고정해 둔 관제 · 컨시어지 값이 베타에도 그대로 적용된 것 아닌지 확인 부탁드립니다.)

## 1. 확인한 것 — 왜 그렇게 보였나

목업용 고정값이 베타에 새어 들어간 것은 아니다. 원인은 베타의 구조 두 가지였다.

| 보인 것 | 원인 |
|---|---|
| 가입 코드가 달라도 한 가족 · 한 기록으로 묶인다 | **관제 센터 하나가 가구 기록 하나**(`HH-C1`)를 썼다. 가입 코드는 '어느 센터'만 정했고, `코드 바꾸기`는 옛 코드를 막을 뿐 새 공간을 만들지 않았다. 계정마다 가구 번호 칸(`accounts.household_id`)은 있었지만 가입 때 늘 센터의 가구 번호를 넣었고, 로그인도 센터의 가구를 세션에 실었다 |
| 모두 같은 컨시어지가 담당으로 보인다 | 관제가 담당을 지정하기 전에는 **그 센터에 먼저 가입한 컨시어지**를 담당으로 보여 주는 규칙이 있었다 (`lib/people.js` — `concierges[0]`). 가구가 하나일 때는 문제가 없었지만 사실상 '자동 지정'이었다 |
| 모두 같은 관제 | 이것은 맞는 동작이다 — 같은 센터에 가입한 사람은 그 센터 관제가 맡는다. 다만 관제 화면도 가구 하나만 보는 구조였다 |

데모(로그인 없이 보는 시연)의 예시 인물 · 예시 숫자는 센터 공간에 나오지 않는다 (2026-10-06 에 막았고 이번에도 다시 확인했다).

## 2. 바꾼 것

한 관제 센터 안에 **가족이 여럿**이고, 가족마다 기록(약 · 일정 · 부탁 · 마음사서함 · 결제 · 리포트 · 음성 · 활동 기록)이 따로 쌓인다.

| 무엇 | 내용 |
|---|---|
| 가족 가입 코드 | 가족마다 하나. **같은 코드로 가입한 어르신 · 보호자가 한 가족, 코드가 다르면 다른 가족**이다. 관제 › `가족 관리`에서 `[가족 추가]`로 만든다 |
| 센터 가입 코드 | 계정 · 권한에 있던 코드. 이제 **직원(컨시어지 · 파트너 · 관제) 가입에만** 쓴다. 서로 바꿔 적으면 가입 화면이 어느 코드가 필요한지 알려 준다 |
| 가족 초대 링크 | 그대로 — 초대받은 사람은 보낸 사람의 가족으로 들어간다 |
| 관제 화면 | 머리의 `가족` 칸에서 가족을 고르면 화면 전체가 그 가족의 기록으로 바뀐다. 새 메뉴 `가족 관리`(목록 · 추가 · 가입 코드 · 구성원 · 담당 · 요금제 · 지금 상황). 계정 · 권한 회원 목록에 `가족` 칸과 `[옮기기]` |
| 다른 가족의 긴급 | 지금 보고 있지 않은 가족의 SOS · 도와줘요는 화면 맨 위 띠와 알림음으로 알린다 (15초 간격). 승인 대기 · 담당 미지정은 '지금 처리할 일'에 올린다 |
| 담당 컨시어지 | **관제가 지정한다 — 자동으로 정하지 않는다.** 지정 전에는 '담당 컨시어지 지정 전'이 관제 '지금 처리할 일'에 뜬다 |
| 컨시어지 화면 | 관제가 주 · 부 담당으로 지정한 가족만 보인다. 담당 가족이 여럿이면 `가족` 칸에서 고른다. 하나도 없으면 "아직 담당 가족이 없습니다" (지정되면 저절로 열린다) |
| 어르신 · 보호자 화면 | 가입한 가족의 기록만. 서버가 로그인 세션의 가구로 정하므로 다른 가족 번호를 붙여 불러도 거절된다 |

SQL 을 한 번 실행해야 한다 (`supabase/families.sql` — 가구 표에 칸 3개 · 색인 · 센터별 보기). 환경변수는 새로 없다.
SQL 실행 전에는 앱이 예전 방식(센터 코드 하나 · 한 가족)으로 그대로 돈다.

### 구조

- 가구 번호: 첫 가족은 예전 그대로 `HH-C1` · `HH-C2` · `HH-C3`, 새 가족은 `HH-C1-K7M2QD`(뒤 6자리 무작위). **번호 앞머리가 센터**라 다른 센터의 가족 번호로는 아무것도 열리지 않는다 (`lib/centers.js`).
- 어느 가족의 기록인지는 서버가 정한다 (`lib/families.js householdOf`).
  어르신 · 보호자 → 로그인 세션의 가구(가입한 가족). 관제 → 고른 가족(`?hh=`)이 그 센터 것인지 확인. 컨시어지 → 고른 가족의 주 · 부 담당인지 확인.
- 직원 화면은 읽을 때도 저장할 때도 가족 번호를 붙여 보낸다. 고른 가족은 **탭마다** 따로 기억한다 —
  탭 둘에 서로 다른 가족을 열어 두어도 한 가족의 기록이 다른 가족에 저장되지 않는다 (검수 항목에 있다).
- 가족 목록의 '지금 상황'(SOS · 도와줘요 · 승인 대기 · 담당 · 요금제)은 서버가 가구 기록에서 필요한 칸만 꺼내 센다 (`lib/family-summary.js`).

## 3. 요청에 없어 정한 것

| 정한 것 | 내용 | 이유 |
|---|---|---|
| 가족을 묶는 기준 | 가족 가입 코드 하나 = 한 가족 | 현장 테스트가 기대한 그대로다 ("코드가 다르면 다른 가족"). 상담 → 가족 추가 → 코드 전달 → 가입 → 승인 순서가 실제 영업 흐름과도 맞는다 |
| 센터 코드로 어르신 · 보호자가 가입하면 | 받지 않고 "가족 가입 코드를 받아 적어 주세요" | 받으면 다시 첫 가족에 묶인다 — 이번 문의와 같은 일이 되풀이된다 |
| 예전부터 쓰던 공간 | 그 센터의 **첫 가족**으로 그대로 둔다 (기록 · 회원 그대로) | 기록을 누구 것으로 나눌지 프로그램이 정할 수 없다. 관제가 `[옮기기]`로 사람을 나눈다 |
| 가족 옮기기 | 사람만 옮긴다. 남긴 기록은 원래 가족에 남는다 | 기록은 가족의 것이고 증명이다 (10-18 원칙). 옮겨진 사람은 15초 안에 화면이 멈추고 다시 로그인하면 새 가족이 열린다 |
| 담당 컨시어지 | 자동 지정을 없앴다. 첫 가족도 지정해야 한다 | 문의가 지적한 것이 '자동 지정'이다. 가족마다 규칙이 다르면 더 헷갈린다 |
| 컨시어지가 보는 범위 | 주 · 부 담당인 가족만 | 맡지 않은 가족의 건강 · 연락 기록을 볼 이유가 없다 (개인정보 최소 열람) |
| 관제가 보는 범위 | 그 센터의 모든 가족. 관제 회원도 가족 추가 · 옮기기를 한다 | 승인 · 정지와 같은 수준의 일이다. 빈 가족 지우기만 센터 관리자(`ops1~3`) |
| 빈 가족 지우기 | 구성원이 없고 기록을 한 번도 저장하지 않은 가족만 | 잘못 만든 가족 정리용. 기록이 있는 가족은 지우지 않는다 |
| 가족 이름 | 관제가 적은 이름 → 없으면 "○○ 님 가족"(먼저 가입한 어르신) → "새 가족" | 관제 · 컨시어지 화면에서만 쓴다. 가입 코드를 확인하는 화면에는 가족 이름을 내보내지 않는다 |
| 파트너(영업) 화면 | 그대로 첫 가족을 본다 | 가족 기록을 쓰지 않는 화면이다 — 추천 코드 · 상담 연결은 따로 정해야 한다 |
| 한 가족에 어르신 두 분 | 기록은 한 벌, 화면의 어르신은 먼저 가입한 분 | 부부 가구 요금 · 기록 방식이 아직 '상담에서 안내'다 (11-10). 다른 댁이면 관제 화면이 나누라고 알린다 |
| 직원을 어르신 · 보호자로 바꿀 때 | 계정에 적힌 가족(직원으로 가입했으면 첫 가족)에 들어간다. 확인 창이 어느 가족의 기록을 보게 되는지 미리 알린다 | 역할 변경에서 가족까지 고르게 하면 창이 복잡해진다 — 바꾼 뒤 `[옮기기]`로 옮긴다 |

## 4. 배포한 뒤 관제가 한 번 해야 하는 일

1. Supabase SQL Editor 에서 `supabase/families.sql` 실행 → zip 덮어 올리기 (순서는 바뀌어도 된다).
2. 관제(`ops1`) › **가족 관리** — 첫 가족에 `[코드 만들기]`, 따로 쓸 가족마다 `[가족 추가]`.
3. 관제 › **계정 · 권한** — 지금 한 가족에 묶여 있는 어르신 · 보호자를 `[옮기기]`로 각 가족에 나눈다
   (연습 계정이면 지우고 가족 가입 코드로 다시 가입해도 된다).
4. 가족마다 **가족 열기 → 어르신 관리** 에서 `[담당 컨시어지 변경]` · `[요금제 지정]`.
   담당을 지정하기 전에는 컨시어지 화면이 "아직 담당 가족이 없습니다"로 보인다.
5. 앞으로 어르신 · 보호자에게는 가족 관리의 **가족 가입 코드(링크)** 를 보낸다. 예전에 나눠 준 이용자 가입 링크(센터 코드)는 더 쓰지 못한다.

## 5. 아직 아닌 것 · 알아 둘 것

- **관제 화면은 한 번에 한 가족이다.** 여러 가족을 한 화면에 모아 보는 것은 가족 목록의 '지금 상황'(SOS · 도와줘요 · 승인 대기 수 · 담당 · 요금제)까지다.
  방문 · 해주세요 · 일정을 여러 가족에 걸쳐 한 표로 보려면 가구 기록을 표로 나누는 실서비스 DB 로 옮겨야 한다 (`docs/DB-SCHEMA.md`).
- **가족 수가 수십 곳을 넘으면** 가족 목록이 느려질 수 있다 — 15초마다 가족마다 가구 기록에서 칸을 꺼내 세기 때문이다. 정식 판매 초기 규모에서는 문제없지만 같은 이유로 DB 를 나눠야 한다.
- **상담 신청 → 가족 만들기는 손으로 잇는다.** 상담 신청 목록에서 가족이 저절로 생기지 않는다.
- **담당은 이름으로 맞춘다.** 한 센터에 이름이 같은 컨시어지가 둘이면 둘 다 담당으로 읽힌다 — 이름을 다르게 적어 가입시킨다.
- 담당이 바뀌면 그 컨시어지의 열람은 같은 서버에서는 바로, 다른 서버 인스턴스에서는 15초 안에 바뀐다.
- 센터는 여전히 셋(`ops1~3`)이다. 센터를 늘리는 것 · 지점 개념은 이번 범위가 아니다.
- 관제 PC 에만 남기는 보조 기록(SOS 사건 메모 등)은 가구 번호별 칸이라 가족마다 따로다.
