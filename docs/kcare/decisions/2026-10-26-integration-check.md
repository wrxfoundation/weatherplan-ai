# 연동 점검 — 어르신 본인 결제가 보호자에게 결제 요청을 보내던 것 (2026-10-26)

근거: 연동 확인 중 받은 오류 보고.

> [정상 로직]
> A. 본인 결제 선택: 어르신 앱 화면에서 바로 결제 모듈(PG) 실행, 보호자 푸시/카톡 알림 실행 X
> B. 가족에게 부탁 선택: 어르신 앱 결제창 미실행, 보호자 앱/카톡으로 결제 요청 링크 및 알림 발송
>
> [현재 발생 중인 오류] 어르신이 '본인 결제'를 눌렀는데도 어르신 결제창과 함께 보호자 스마트폰에도 결제 요청 알림/창이 열린다.

새 환경변수 · SQL 은 없다. 기록 모양도 그대로다 (`payAsk` 는 2026-10-19 부터 있던 칸).

## 1. 원인과 고친 것

- **원인**: 보호자 앱이 `결제 대기(awaitingPayment)` 인 해주세요를 **누가 내기로 했는지 보지 않고** 모두 보호자 할 일로 띄웠다 —
  홈 `결제 · 수락 대기 n건` 카드, 해주세요 맨 위 큰 결제 카드와 `결제하기` 버튼. 어르신이 '제가 결제할게요'를 누르면 요청이 결제 대기로 저장되고
  (어르신 폰은 바로 결제창으로), 보호자 폰은 4초 안에 그 기록을 받아 결제 요청으로 보였다. 결제 화면 · 결제 서버도 보호자의 결제를 막지 않았다.
  어르신 앱 쪽(본인 결제는 결제창으로, 가족 부탁은 결제창 없이 `payAsk` 를 남김)은 맞게 동작하고 있었다.
- **규칙 한 곳** — `lib/requests.js` `payerOf(r)` · `guardianPays(r)`:
  - 어르신이 낸 해주세요, 어르신이 수락한 선생님 제안 → **어르신이 낸다**. 어르신이 `가족에게 결제 부탁`을 누른 것(`payAsk`)만 보호자가 낸다.
  - 보호자가 낸 해주세요, 보호자가 수락한 제안(승인 대상이 정해지지 않은 예전 제안 포함), 관제 안내 → 보호자가 낸다.
- **이 규칙을 보는 곳**:

| 곳 | 전 | 지금 |
|---|---|---|
| 보호자 홈 `결제 · 수락 대기` 카드 | 결제 대기면 모두 | 보호자가 낼 것 + 보호자가 답할 제안만 |
| 보호자 해주세요 큰 결제 카드 · `결제하기` | 결제 대기면 모두 | 같은 기준. 어르신 본인 결제 건은 진행 중 목록 한 줄 `○○ 님이 결제하실 차례예요`(펼침 `○○ 님 부탁 · 직접 결제`) · 결제 버튼 없음 |
| 결제 화면 `/pay` | 막지 않음 | 보호자가 어르신 본인 결제 건을 열면 `어르신이 직접 결제하기로 한 요청입니다. 어르신 화면에서 '가족에게 결제 부탁'을 누르시면 여기서 결제할 수 있어요.` |
| 결제 서버 (`/api/payments/order` · `confirm`) | 가족 누구나 | 같은 경우 403 `ELDER_PAYS` — 화면을 거치지 않은 요청도 막는다. 어르신은 부탁한 뒤에도 직접 낼 수 있다 |
| 관제 지금 처리할 일 · 해주세요 관리 결제 칸 | `가족 결제 대기` | `어르신 결제 대기` / `가족 결제 대기` |
| 컨시어지 해주세요 `가족 결제 대기` 묶음 | 제목 `가족 결제 대기` | 제목 `결제 대기` · 줄마다 `어르신 결제` / `가족 결제` |

- 어르신이 결제창을 닫고 나와도 요청은 결제 대기로 남는다. 어르신 해주세요 › 부탁해 둔 것의 `n원 결제하기` · `가족에게 결제 부탁하기` 가 그대로 있고,
  부탁을 누르는 순간 보호자 폰에 결제 요청이 간다(A → B 로 바꾸기).
- 어르신이 수락한 선생님 제안(돈이 드는 것)도 같은 규칙이다 — 수락만으로는 결제창이 열리지 않고, 어르신이 결제하거나 가족에게 부탁한다. 부탁하기 전에는 보호자에게 결제 요청이 가지 않는다.
- 같이 고친 것: 보호자 큰 카드 `김순자 님 님이 결제를 부탁했어요` → `김순자 님이 결제를 부탁했어요` (부탁한 사람 이름에 이미 '님'이 들어 있었다).

### 아직 없는 것 (이번 보고와 별개)

- 보호자 **푸시 · 카카오 알림톡**은 아직 연결 전이다 (`관제 › 연동 상태` '알림톡 — 연동 대기'). 지금 '알림'은 보호자 앱 화면의 카드다.
  알림톡을 붙일 때는 `status === "awaitingPayment"` 가 아니라 **`guardianPays(r)`** 가 참이 될 때(= 보호자가 낼 결제가 생겼을 때) 보내야 같은 오류가 다시 나지 않는다.
  가구 기록에 들어오는 동작으로 보면: `addRequest` 의 요청에 `payAsk` 가 있을 때(어르신 '가족에게 결제 부탁') · `askPrimaryPay`(결제 대기 중에 부탁으로 바꿈) ·
  보호자가 낸 요청 · 보호자가 답할 제안. 어르신 본인 결제(`payAsk` 없는 어르신 요청)는 보내지 않는다.
- **`pushEvent` 는 푸시가 아니다** — 이름과 달리 관제 화면의 실시간 접수 줄(`state.ticker`, 40건)에 한 줄을 남기는 동작이다. 어르신 본인 결제에도
  `pushEvent`('… · 어르신 결제 60,000원')가 함께 저장되므로, 이 동작을 보고 보호자 푸시를 보내면 이번과 같은 오류가 난다.

## 2. 확인

- 고치기 전 코드로 같은 '폰 두 대' 테스트를 돌려 오류를 재현했다 — 어르신 '제가 결제할게요' 뒤 보호자 폰 홈에 `결제 · 수락 대기` 카드 · `결제하기` 버튼 (4건 실패),
  고친 뒤 같은 테스트 15/15.
- 데모 화면 E2E 36(390 · 360px 모두): A 본인 결제(어르신 결제창 · 보호자 홈 · 해주세요 · 결제 화면 막힘) · A→B 나중에 부탁 · B 처음부터 부탁 · 어르신이 수락한 제안.
- 규칙 단위 27(누가 내나 10 · 보호자 할 일 6 · 결제 서버 11). `npm run verify`(린트 경고 0 · 빌드) · `npm run smoke`(40화면 × 2폭 + 눌러서 여는 화면 5 × 2폭).
- 실제 저장 모드(Postgres + PostgREST) 테스트 환경은 이번 컨테이너에 없어 돌리지 못했다 — 결제 서버 규칙은 단위 확인으로 대신했다.

## 3. 전수점검 — 결제 밖의 로직까지 (같은 날)

근거: 같은 날 받은 요청 "다른 로직도 이상 없는지 전수점검해봐".

네 영역으로 나눠 코드를 읽고, 기록 규칙(`lib/state.js` reducer)을 직접 돌려 봤다.
① 해주세요 · 결제 · 환불 ② 스토어 · 추가 이용 금액 · 멤버십 ③ 저장 · 동기화 · 권한 ④ 역할 사이 알림 · SOS · 일정 · 음성.
문서(결정 기록 · 테스트 시나리오 · 코드 주석)에 근거가 있는 것은 고쳤다. 규칙이 적혀 있지 않은 것은 고치지 않고 §3-4 에 모았다.
새 환경변수 · SQL 은 없다. 가구 기록(`households.state`, JSON)에는 칸이 몇 개 늘었다:
`pendingOrders`(사람별 장바구니) · 요청의 `storeOrder` · 일정의 `reBy`(확정 뒤 바꾼 쪽).

### 3-5. 확인한 것 · 못 한 것

- 기록 규칙 단위 검사 — 점검 항목 42개 · 결제자 27개.
  서버가 가구 기록에 결제를 남기는 것은 가짜 DB 로 확인했다: 버전이 엇갈리면 다시 읽어 넣고, 같은 주문번호는 두 번 넣지 않는다.
- 데모 화면 E2E — 점검 항목 27개, 결제자 A/B 36개.
- 테스트 가구 흉내 E2E (로그인 빌드 · 세션과 가구 저장 API 는 테스트가 흉내) — 점검 5개, 결제자 15개.
  충돌(409) 직후 바로 다시 보내도, 로그아웃 직전에 저장해도 다른 폰이 저장한 것이 남는다.
- `npm run verify`(린트 경고 0 · 빌드) · `npm run smoke`(40화면 × 2폭 + 눌러서 여는 화면 5 × 2폭).
- **실제 토스 · Supabase 로는 돌리지 못했다** — 이 컨테이너에는 그 환경이 없다. 연동 테스트에서 함께 봐야 할 것:
  - M-2 의 토스 결제 조회 복구
  - 결제 서버가 `households` 에 직접 쓰는 것
- 고치지 않은 것 (낮음):
  - 관제 PC 두 대에서 지난 SOS 사건을 닫으면 지금 SOS 가 꺼질 수 있다. 사건 닫기가 지금 SOS 시각을 넘기기 때문이다 — 확인하지 못했다.
  - 감사로그는 화면이 보낸 동작 목록으로 쓴다. 한 번 저장에 100건까지만 남고, 다시 보내 무효가 된 동작도 성공으로 남는다.
  - 가입비 '결제 완료' 판정이 결제 상태 · 환불을 보지 않는다. 가입비 가격이 확정 전이라 아직 영향은 없다.
